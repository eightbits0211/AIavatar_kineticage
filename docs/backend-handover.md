## 0.1 The 60-second mental model

```
                 ONE REQUEST'S JOURNEY
  Mobile / web -> Express -> rateLimit(600/min) -> authMiddleware(Firebase JWT) -> route
                                                                                    |
                                                                                    v
                                                                        service(s) -> MongoDB
                                                                                    |
   Two things a route might do with the AI layer:                                   v
   - generate a workout  -> Rules Engine (deterministic, NO AI)   the "what"    response JSON
   - talk to the user    -> Gemini (text) / Gemini Live (voice)   the "how it feels"
```

The whole product is that split. **Workout content is computed, never generated by AI.** The AI only ever explains and motivates. If you keep that one rule in your head, the codebase makes sense.

Typical end-to-end flow: `sign in -> onboard (metrics + persona) -> generate bundles -> pick one -> start session -> coached via text/voice -> end session (XP, streak, badges, calories, auto-regenerate next bundles)`.

## 1. What KineticAge is

An AI fitness companion. The user onboards, gets 3–4 personalized workout "bundles", starts a session, and is coached through it by "Kin" via text or real-time voice. The app tracks progress, calories, XP, streaks, and badges.

### The core design philosophy (read this — it explains everything)

There are **two deliberately separated systems**:

1. **The Rules Engine** — a deterministic, trainer-approved pipeline that decides *what* the workout is (which exercises, sets, reps, rest). It is **not** an LLM. Given the same inputs it produces safe, explainable, predictable output. This is what protects users from unsafe or hallucinated workouts.

2. **The AI layer (Google Gemini)** — decides *how the workout feels*. It explains exercises, motivates, answers questions, and coaches. It **never** invents exercises or prescribes weights.

Everywhere in the code you'll see this separation enforced. When in doubt: content = Rules Engine, conversation = Gemini.

### AI providers

The project originally evaluated Anthropic Claude but **shipped on Google Gemini**. Current state:
- **Text chat** → Gemini `gemini-2.5-flash` (`services/aiCompanion.ts`, renamed from the old `claude.ts`)
- **Real-time voice** → Gemini Live `gemini-3.1-flash-live-preview` (`services/voiceLiveProxy.ts`)
- **Speech-to-text** (tap-to-talk fallback) → Deepgram `nova-2`
- **Text-to-speech** (text replies + fallback) → ElevenLabs `eleven_flash_v2_5`

> The companion is named **"Kin"** consistently across the backend, prompts, and frontend. (An earlier draft of the base prompt used "Kira"; that was unified to "Kin" on 15 Jul 2026.)

## 5. Deployment (Render)

- **Host:** Render, auto-deploys branch `dev`. Needs GitHub repo access for push webhooks; without it, use **Manual Deploy** after each merge.
- **Build command:** `npm install --include=dev && npm run build`
  - `--include=dev` is required: with `NODE_ENV=production`, npm skips devDependencies, but `typescript` and `@types/*` live there and are needed to compile (otherwise `TS7016` errors).
- **Start command:** `npm start`
- **Port:** reads `process.env.PORT` (Render assigned 10000).
- **WebSockets:** the host must support long-lived WS for the voice proxy at `/ws/voice-live`. Render does.
- **Cold start:** free tier sleeps when idle; first request after idle takes ~30–90s. Warm it (`/health`) before demos.
- **Seed prod:** run the seed script pointed at the production `MONGODB_URI` once, or the Rules Engine will throw.

**Rule of thumb:** a `server/**` change needs a **redeploy only** — the mobile app calls the backend over the network, so no APK rebuild is needed for backend changes. A `mobile/**` change needs a new EAS build.

## 6. Architecture & request flow

```
Mobile app / browser
        │  HTTPS (REST)  +  WSS (voice)
        ▼
┌──────────────────────────────────────────────┐
│ Express app (src/index.ts)                     │
│  1. CORS                                        │
│  2. express.json()                              │
│  3. rateLimitMiddleware  (600/min per user)     │
│  4. route → authMiddleware (Firebase JWT)       │
│  5. route handler → service(s) → MongoDB        │
│                                                 │
│  WS server on /ws/voice-live → voiceLiveProxy   │
└──────────────────────────────────────────────┘
        │
        ├── MongoDB Atlas (Mongoose)
        ├── Gemini API (text) + Gemini Live (voice, WS)
        └── Deepgram (STT) + ElevenLabs (TTS)
```

- Every REST route (except `/health` and the `/api/voice-demo/*` test routes) is behind `authMiddleware`.
- All external API calls (Gemini, Deepgram, ElevenLabs) are wrapped in `p-retry` and fall back gracefully — the app returns friendly messages instead of 500s when a third party hiccups.

## 8. The Rules Engine (`services/rulesEngine/`)

Deterministic workout generation. Entry point: `generateBundles({ user, recentMuscleGroups?, seed? })` in `index.ts`. It loads all exercises from Mongo and runs 4 stages in order. **No LLM is involved.**

### Stage 1 — Filter (`filterStage.ts`)
Narrows the full library to eligible exercises. Priority order: **Injury > Location > Equipment > Intensity > Fitness Level.**

- **Injury:** exclude if any of the exercise's `contraindications` matches a user injury (excluding `none`).
- **Location:** exercise's `location_compatible` must include the user's location. `hybrid` bypasses this filter (can access everything).
- **Equipment:** `none` = bodyweight, always allowed. Otherwise the user must own at least one required item.
- **Intensity (MHR safety gate):** max allowed zone by age/MHR:
  - age ≥ 60 OR MHR < 140 → cap at `moderate`
  - age ≥ 50 OR MHR < 155 → cap at `high`
  - else → `very_high` allowed
  - (zone ranks: low 0, moderate 1, high 2, very_high 3)
- **Fitness level:** beginner → only beginner; intermediate → beginner+intermediate; advanced → all. **Exception:** `warm_up` and `cool_down` exercises are never filtered by fitness level.

### Stage 2 — Category (`categoryStage.ts`)
Maps the user's `fitness_goal` to a workout category and applies set/rep/rest parameters. Keeps exercises tagged with the goal **plus** always keeps structural phases (warm_up, cool_down, core, cardio_finisher, bmi_targeting, balance_mobility). Parameters come from each exercise's `default_set_rep_range[goal]`; fallback is general_fitness, then hardcoded `{sets:3, rep_min:8, rep_max:12, rest_seconds:60}`. Compound detection: ≥2 primary muscles, or a primary in `[quadriceps, glutes, hamstrings, chest, upper_back, lats, full_body]`.

### Stage 3 — Persona Modifier (`personaModifier.ts`)
Additive tweaks based on persona tags (cumulative — multiple tags all apply):
- `complete_beginner`: reduce sets by 1 (min 2); sort beginner-difficulty first.
- `office_professional`: add 1 posture mobility exercise (targets thoracic_spine/hip_flexors/neck/upper_back) if none present.
- `injury_recovery_user`: per injured area, add 1 non-contraindicated rehab mobility exercise. Mapping: knee→[quadriceps,hamstrings,hip_flexors], lower_back→[spine,core,hip_flexors], shoulder→[rotator_cuff,upper_back,thoracic_spine], wrist→[forearms], ankle→[calves], neck→[neck,upper_back].
- Other personas (regular_gym_goer, weight_loss_seeker, home_workout_user, ai_companion_seeker, inconsistent_enthusiast): no workout changes (they only affect AI tone).

### Stage 4 — Bundle Assembly (`bundleAssembly.ts`)
Builds 3–4 bundles following a fixed slot sequence per duration:
- **15 min:** warm_up×1, primary×1, core×1, cool_down×1
- **30 min:** warm_up×1, primary×2, core×1, cardio_finisher×1, cool_down×1
- **45 & 60 min:** warm_up×1, primary×2, bmi_targeting×1, core×1, cardio_finisher×1, cool_down×1

Details:
- **Bundle count:** 4 if ≥20 modified exercises available, else 3 (capped at 4).
- **Variety:** primary/bmi_targeting exercises are globally unique across bundles; within a slot, avoids repeating substitution groups. `PHASE_FALLBACKS` fills unfillable slots from related phases; a bundle with <3 exercises is skipped.
- **BMI slot preference** (bmi_targeting): underweight→strength/hypertrophy; normal→general/strength; overweight→weight_loss/general (lower impact); obese→low-impact bodyweight-friendly.
- **Determinism:** pass a `seed` string → mulberry32 PRNG makes generation reproducible. No seed → `Math.random` (variety each time).
- **Calorie estimate:** low = duration×5, high = duration×8.
- **Titles** by primary muscle: Push Power / Pull Strength / Lower Body / Full Body Blast, else cycles generic names.
- **Recommendation:** each bundle scored (+2 per muscle NOT in `recentMuscleGroups`, + count of unique muscles); highest score gets `is_recommended = true`.

**Fallbacks in `index.ts`:** if <3 exercises pass the filter, it adds all bodyweight/no-equipment exercises; if the category yields <3, it retries with `general_fitness`.

## 9. Persona service (`services/persona.ts`)

### Persona tags (assigned at onboarding; a user carries 2–4, not mutually exclusive)

| Tag | Condition |
|-----|-----------|
| `complete_beginner` | `sedentary` AND no prior program |
| `regular_gym_goer` | (`moderately_active` or `very_active`) AND `gym` AND prior program |
| `weight_loss_seeker` | goal = `weight_loss` |
| `strength_training_user` | goal = `strength` |
| `home_workout_user` | location = `home` AND equipment ⊆ {none, dumbbells, resistance_bands, exercise_mat} |
| `office_professional` | (`sedentary` or `lightly_active`) AND duration ∈ {15, 30} |
| `injury_recovery_user` | any injury reported (not all `none`) |
| `ai_companion_seeker` | talkativeness = `high` |
| `inconsistent_enthusiast` | **behavioral** — NOT set at onboarding. `evaluateInconsistentEnthusiast`: completed sessions in last 14 days ÷ (statedDaysPerWeek × 2) < 0.5 |

### Metric formulas (`calculateMetrics`)

- **BMI** = `weight_kg / (height_m)²`, rounded to 1 decimal. Category: <18.5 underweight, <25 normal, <30 overweight, else obese.
- **BMR (Mifflin-St Jeor):** male = `10·w + 6.25·h − 5·age + 5`; female = `… − 161`; other = average of the two.
- **Activity multipliers:** sedentary 1.2, lightly_active 1.375, moderately_active 1.55, very_active 1.725.
- **TDEE** = BMR × multiplier; **tdee_range** = ±5% (low ×0.95, high ×1.05).
- **MHR** = `220 − age`; **target_zone** = 60%–80% of MHR.

## 10. Gamification (`services/gamification.ts`)

### XP values
| Action | XP |
|--------|-----|
| Full workout | 50 |
| Partial workout (≥50%) | 25 |
| Abandoned (<50%) | 0 |
| Each progression milestone | 20 |
| First workout (one-time) | 30 |
| 7-day streak | 100 |
| 30-day streak | 500 |
| Daily check-in | 10 |
| Onboarding complete (one-time) | 15 |

### Levels
Level N requires **cumulative N × 200 XP**. (Level 1: 0–199, Level 2: 200–599, Level 3: 600–1199, …). `xpForNextLevel()` returns current level, XP into level, and XP needed for the next.

### Streaks (grace-day model, `updateStreak`)
- No prior workout → streak = 1.
- Same day → unchanged.
- Exactly 1 day gap → streak + 1.
- Exactly 2 day gap AND no grace day used this week → streak + 1, grace day consumed (1 grace day/week).
- Otherwise → streak resets to 1.
- Milestones: reaching 7 → +100 XP, reaching 30 → +500 XP.

### Badges (7, `evaluateBadges` returns only newly earned)
`first_step` (1st workout), `consistency_starter` (3 in 7 days), `week_warrior` (7-day streak), `momentum` (30-day streak), `comeback` (return after 7+ day gap), `leveling_up` (1st progression milestone), `goal_getter` (10 workouts in goal category).

## 11. Progression state machine (`services/progression.ts`)

Runs on session end for each completed/skipped/pain-stopped exercise. States: `stable`, `ready_to_progress`, `deload_candidate`. History capped at 10 sessions.

- **Progress up:** on a completed exercise where all completed sets hit `rep_max`, `consecutive_top_completions` increments (1 → state `ready_to_progress`). At **2 consecutive**: if `rep_max < 15` → bump `rep_min` and `rep_max` by 1 (flag `rep_increase`); else add a set (flag `set_increase`). Counter resets, state back to `stable`.
- **Fast-track:** `felt_easy` feedback pre-sets the top-completion counter to at least 1, so the next top-of-range hit progresses immediately.
- **Deload:** `felt_hard`, `skipped`, or `pain_stopped` increments `consecutive_skips_or_hard`. At **≥2** → state `deload_candidate`, flag `deload` (exercise gets reduced/substituted in future), counter resets.

## 12. Session lifecycle (`routes/session.ts`)

Status flow: `in_progress` → `full` | `partial` | `abandoned`.

- **POST `/api/session/start`** `{bundle_id}` — creates a Session with each bundle exercise expanded into `sets`. If an `in_progress` session already exists: resume it, unless it's older than **4 hours** (then mark abandoned and start fresh).
- **PUT `/api/session/:id/exercise`** `{exercise_id, action, data}` — actions:
  - `complete_set` `{set_number, actual_reps}` → logs reps, marks set done, status → in_progress
  - `complete_exercise` `{feedback?}` → status → completed
  - `skip` `{reason?}` → status → skipped
  - `pain` `{body_area}` → status → pain_stopped, pushes a pain event
  - `feedback` `{feedback}` → sets feedback only
- **POST `/api/session/:id/end`** — computes completion ratio (=1 full, ≥0.5 partial, else abandoned), then: runs progression, calculates XP, updates streak/level, evaluates badges, computes calories, and **auto-regenerates bundles** for next time (deactivates old active bundles, generates new, with one retry after 2s). Returns a full summary (status, completion %, calories, XP + breakdown, level, streak, progression flags, badges earned).
- **POST `/api/session/:id/pause`** — records `paused_at`.
- **GET `/api/session/active`** — returns the in-progress session for resume; if paused > **30 minutes**, marks it abandoned.

### Calorie formula (on end)
`weightMultiplier = userWeight/70` (default 70kg). For each completed/in-progress exercise: sum actual reps (or the target midpoint if a set was marked done without reps) × a per-rep rate for the primary muscle × weightMultiplier. Per-rep rates: quads/glutes 0.20, hamstrings 0.18, chest/upper_back/lats 0.15, shoulders 0.12, core/hip_flexors 0.10, biceps/triceps/calves 0.08, forearms 0.06, full_body 0.25, lower_back 0.12, cardiovascular_system 0.30 (default 0.12). Plus a base `durationMin × 2 × weightMultiplier`. Fallbacks: bundle mid-estimate × completion ratio, or `durationMin × 6 × ratio`.

## 13. AI companion — text (`services/aiCompanion.ts`)

- **Model:** `gemini-2.5-flash` via `@google/generative-ai`.
- **generationConfig:** `maxOutputTokens: 500`, `temperature: 0.7`, `thinkingConfig: { thinkingBudget: 0 }`.
  - The thinking budget is disabled on purpose: Gemini 2.5 Flash was spending ~370 hidden "thinking" tokens per reply, causing latency and mid-sentence truncation. Disabling it made replies fast and complete. Quality is unaffected for conversational coaching (the actual reasoning is done deterministically by the Rules Engine).
- **Retry:** `p-retry` with `retries: 3, minTimeout: 1000, factor: 2`. On total failure returns a friendly fallback message (`fallback: true`), never throws.
- **Action intents:** replies may end with `[ACTION:name]`; the service parses it into `action_intent` and strips it from the text.
- **Safety post-processing (always applied):**
  - `stripWeightValues` — regex-replaces any `\d+\s*(kg|lbs|…)` with `"[a weight that feels manageable]"` so the AI never prescribes a specific weight.
  - `stripMarkdown` — removes bold/italic/headers/bullets/code so text is clean for TTS.

Used by `routes/companion.ts` (chat), `routes/companionTrigger.ts` (proactive coaching triggers), and bundle rationale generation.

## 14. Voice — Gemini Live proxy (`services/voiceLiveProxy.ts`)

The most complex service. It's a **server-side WebSocket proxy** sitting between the client and Gemini Live:

```
client  ⇄  /ws/voice-live (our proxy)  ⇄  Gemini Live API
```

The proxy authenticates the user, builds the full system prompt (persona + Rules Engine data + session state), opens a WS to Gemini, relays audio both ways, intercepts Gemini's function calls to update MongoDB, and persists conversation turns.

- **Model:** `gemini-3.1-flash-live-preview`. `responseModalities: ['AUDIO']`.
- **Auth:** `?token=<firebaseIdToken>` query param. No token → demo mode (`uid = '__demo__'`, loads any onboarded user) — for testing only.
- **Voice style → Gemini voice:** calm→Aoede, energetic→Kore, friendly→Puck (default), professional→Charon.
- **VAD (`realtimeInputConfig.automaticActivityDetection`):** `startOfSpeechSensitivity: LOW`, `endOfSpeechSensitivity: LOW`, `prefixPaddingMs: 300`, `silenceDurationMs: 800`. LOW start sensitivity was set to stop false barge-in (Kin was cutting off mid-sentence when the mic picked up echo/noise).

### The 3 modes (chosen from user + session state)
- **`onboarding`** — user hasn't completed onboarding. Kin collects profile fields conversationally (see 14.2).
- **`workout`** — an `in_progress` session exists. Kin asks resume-or-fresh, then coaches.
- **`chat`** — has a bundle (or none) but no active session. Kin chats / helps pick a workout.

### 14.1 Gemini function-calling tools (deterministic voice actions)
Instead of fragile phrase-matching, Gemini is given these functions and calls them based on user intent. Each handler updates the session and emits a client event.

| Function | What it does |
|----------|--------------|
| `start_workout(bundle_choice)` | Starts a session (matches choice by title / "recommended" / number / ordinal) |
| `complete_set(actual_reps?)` | Marks the current set complete |
| `next_exercise()` | Marks current exercise **completed** and advances |
| `skip_exercise(reason?)` | Marks current exercise **skipped** (without doing it) |
| `pause_workout()` | Sets session status `paused` |
| `resume_workout()` | Sets session status back to `in_progress` |
| `end_workout()` | Emits end events so the frontend runs its REST end flow (single source of truth for XP/badges/summary) |
| `report_pain(body_area)` | Marks exercise `pain_stopped`, records pain |

### 14.2 Events emitted to the client (message `type` values)
`context_loaded`, `onboarding_progress`, `onboarding_type_fallback`, `onboarding_complete`, `onboarding_error`, `bundles_generated`, `bundles_generation_failed`, `workout_state` (with `action`: `paused`/`resumed`/`ended`/`exercise_complete`/`skipped`/`pain`), `session_end`, `session_started`.

### 14.3 Voice onboarding (`services/voiceOnboarding.ts`)
- **12 fields, in order:** `name, age, gender, height, weight, fitness_goal, activity_level, workout_location, equipment, injuries, workout_duration, prior_experience`.
- Extraction happens on the **user's** speech (input transcription), not Gemini's output, via per-field regex/keyword parsers (e.g. height ft/in → cm, weight lbs → kg ×0.4536, age 16–100).
- **Never gets stuck:** after **3 failed extraction attempts** on a field, it's defaulted and onboarding advances (`defaultCurrentFieldAndAdvance`). Escape hatch: user says "just start"/"that's all" with ≥5 fields collected → `completeWithDefaults`.
- **Defaults:** name `Friend`, age 28, gender prefer_not_to_say, height 170, weight 70, goal general_fitness, activity moderately_active, location gym, equipment [dumbbells], injuries [none], duration 30, prior_experience false.
- On completion: saves fields, runs `calculateMetrics` + `assignPersonaTags`, sets `onboarding_completed = true`, grants 15 XP.

## 16. Auth & rate limiting

- **Auth (`middleware/auth.ts`):** initializes Firebase Admin from env; expects `Authorization: Bearer <firebaseIdToken>`; verifies with `admin.auth().verifyIdToken()` and sets `req.uid`. 401 on missing/invalid/expired.
- **Rate limit (`middleware/rateLimit.ts`):** in-memory Map, 600 requests / 60s, keyed on `req.uid` then `req.ip`. Returns 429 when exceeded. Note: rate limiter runs **before** auth, so in dev multiple users can share the IP bucket — hence the high 600 limit. Production should key per-user (after auth) and use Redis.

## 18. Prompt architecture (`prompts/`)

`buildSystemPrompt()` assembles 4 layers:
1. **Base personality** (`basePersonality.ts`, static) — who Kin is, the hard guardrails (never invent exercises, never prescribe weights, never give medical advice, never appearance-based language, strict no-markdown for TTS, pain → stop + `[ACTION:update_injuries]`).
2. **User context** — name/age/goal/persona tags/injuries/preferences, plus a persona-specific tone instruction (9 personas mapped) and a coaching-style instruction (motivational/friendly/strict/zen).
3. **Session context** (per-turn during a workout) — current bundle, exercise, set X of Y, target reps, rest, exercises remaining, instructions.
4. **History** — recent session summaries.

## 19. Known issues, quirks & gotchas (read before changing things)

- **Companion naming is unified to "Kin"** across code, prompts, and docs (was previously "Kira" in the base prompt).
- **Shipped AI is Gemini, not Claude.** Code, the steering file, `README`, `system-design.md`, and `requirements.md` all say Gemini. `ai-trainer-avatar-tech-stack-research.md` is kept as a historical evaluation with a note at the top (it discusses the original Claude decision). The untracked `scripts/generate-report.js` also still references Claude — it's a local doc-generator, not part of the app.
- **Rate limiter runs before auth**, so it keys on IP in practice during dev → the 600/min limit is intentionally high. Move it after auth (per-user) + Redis for real production.
- **`/api/voice-demo/*` routes have no auth** — they're test-only. Remove or protect before any real production use.
- **Voice demo mode** (`?token` absent) loads *any* onboarded user — fine for testing, must never be exposed publicly.
- **Auto-regeneration on session end** deactivates old active bundles and generates new ones. If you see bundles "disappear" after finishing a workout, that's by design; the dashboard exposes a `bundles_stale` flag.
- **Exercise library must be seeded** or `generateBundles` throws `"Exercise library is empty"`.
- **Free-tier cold start** (~30–90s) can fail the first voice WS connect — warm the server first.
- **Session resume windows:** 4 hours for start-time staleness, 30 minutes after an explicit pause.
- **`exercise_id` is a String, not an ObjectId.** In `Exercise` it's a human-readable string (e.g. `push_up`), and `Bundle`/`Session` store that string. Some TypeScript interfaces type nested `exercise_id` as `ObjectId`, but the Mongoose schema is `String` — don't try to `.populate()` or cast it to ObjectId; match on the string.
- **Time is server-local.** Daily check-in "today" and streak day math use the server's clock (`setHours(0,0,0,0)`), not the user's timezone. A user just before midnight in another timezone can get an off-by-one day. Fine for the demo; revisit for production (store user timezone or use UTC consistently).
- **CORS is wide open** (`app.use(cors())` with no origin allowlist). Lock it down before production.
- **No request-validation library.** Routes validate inputs manually (the steering doc mentions zod/express-validator, but they aren't wired in). Keep manual checks consistent, or add a validation layer.
- **Guest users accumulate.** `POST /api/auth/guest` creates a real Firebase user + Mongo doc each call and there's no delete endpoint, so testing/anon usage leaves rows behind. Add a cleanup job for production.
- **`image_url_end` is legacy.** It dates from the 2-frame-animation approach; the final animated GIFs (single `image_url`) don't need it. The field is still present across models/types but is effectively unused — safe to ignore or remove later.
- **`chat.ts` and `demo.ts`** at the server root are standalone CLI dev scripts (interactive companion testing), not part of the running server. Handy for prompt iteration.

### 21.1 How to test auth-protected endpoints (the non-obvious part)

Every `/api/*` route except `/health`, `/api/exercises*`, and `/api/voice-demo/*` requires a **Firebase ID token** in `Authorization: Bearer <token>`. You can't mint one from curl directly, but you can get a real one in two steps without the mobile app:

1. `POST /api/auth/guest` → returns a Firebase **custom token**.
2. Exchange it for an **ID token** via Firebase's REST API using the public web API key:
   ```
   POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithCustomToken?key=<FIREBASE_WEB_API_KEY>
   body: { "token": "<customToken>", "returnSecureToken": true }
   → { "idToken": "..." }
   ```
   The web API key is public (it ships in the client; see `server/public/voice-live.html`). Use `idToken` as the Bearer token for all subsequent calls.

This is exactly how the browser pages authenticate, and it's the recommended approach for any integration test script.

## 24. Quick FAQ

**Where does a workout come from?** `generateBundles()` in `services/rulesEngine/index.ts` → stored as Bundle docs → user picks one → `POST /api/session/start`.

**How do I change how Kin talks?** Edit `prompts/basePersonality.ts` (global) or the persona/coaching maps in `prompts/buildPrompt.ts`.

**How do I add an exercise?** Add it to `seeds/exercises*.json` with full metadata (phases, muscles, equipment, contraindications, `default_set_rep_range`, `substitution_group`, difficulty, image URLs) and re-run the seed. The Rules Engine picks it up automatically.

**Why doesn't the AI ever give a weight?** Hard guardrail in the prompt plus `stripWeightValues` post-processing. Intentional safety feature — don't remove it.

**How do voice commands work?** Gemini Live function calling in `voiceLiveProxy.ts` (Section 14.1), not phrase-matching. To add a voice action, declare a new tool in `getWorkoutTools()` and handle it in the tool-call switch.

**Is anything blocking the demo on the backend?** No. It's deployed and verified end-to-end (text, TTS, and voice) as of 15 July 2026.

## 25. Glossary of domain terms

Vocabulary you'll see all over the code and other docs:

- **Bundle** — one complete, ready-to-do workout option (title, focus, duration, calorie range, ordered exercise list). The Rules Engine produces 3–4 per cycle; exactly one is `is_recommended`. Model: `Bundle`.
- **set_id** — an ObjectId shared by the 3–4 bundles generated together, so a "generation cycle" can be grouped/queried as a set.
- **active (on a bundle)** — whether a bundle is the current live option. On session end, old bundles are set `active: false` and a fresh set is generated.
- **Session** — one attempt at a bundle. Has a `status` (`in_progress` → `full`/`partial`/`abandoned`) and per-exercise, per-set tracking. Model: `Session`.
- **SessionTurn** — a single line of conversation (user or companion, voice or text) persisted for history/context. Model: `SessionTurn`.
- **Persona tag** — an auto-assigned behavioral/attribute label (2–4 per user, e.g. `complete_beginner`). Drives both Rules Engine modifiers and AI tone. Set in `persona.ts`.
- **Workout phase** — the slot an exercise fills in a bundle: `warm_up`, `primary`, `bmi_targeting`, `core`, `cardio_finisher`, `balance_mobility`, `cool_down`.
- **Intensity zone** — an exercise's demand relative to max heart rate: `low`/`moderate`/`high`/`very_high`. Used by the filter stage's MHR safety gate.
- **substitution_group** — a label linking interchangeable exercises. Used to avoid near-duplicate picks in a bundle and to substitute a deload candidate.
- **default_set_rep_range** — per-goal `{sets, rep_min, rep_max, rest_seconds}` stored on each exercise; the category stage reads it.
- **current_prescription** — the user's *current* sets/reps for an exercise in `ExerciseProgression`, which the progression logic bumps over time.
- **progression_state** — `stable` / `ready_to_progress` / `deload_candidate` for a user's exercise.
- **Rules Engine** — the deterministic 4-stage workout generator (Filter → Category → Persona Modifier → Bundle Assembly). No AI.
- **Companion / Kin** — the AI coaching layer (Gemini text + Gemini Live voice). Explains and motivates only.
- **voice_style** — user's chosen voice (calm/energetic/friendly/professional) → maps to a Gemini Live and an ElevenLabs voice.
- **coaching_style** — user's chosen coaching delivery (motivational/friendly/strict/zen) → injected into the prompt.
- **Function calling (voice)** — Gemini Live's mechanism for triggering deterministic workout actions by intent, instead of matching exact phrases.
- **Demo mode (voice)** — connecting to `/ws/voice-live` without a token; loads any onboarded user. Testing only.
- **Grace day** — the streak model allows one missed day per week without breaking the streak.
- **Rules Engine "seed"** (optional arg) — a string that makes bundle generation deterministic/reproducible; without it, generation varies each time. (Unrelated to the DB *seed script*, which loads the exercise library.)
